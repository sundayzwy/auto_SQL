# AutoSQL 离线 SQL 代码优化器 - 设计文档

## 1. 项目概述

### 1.1 产品定位

AutoSQL 是一款 Windows 桌面应用程序，专注于为大数据和数据库开发人员提供离线 SQL 代码优化服务。用户可以将 Impala SQL 或 Oracle SQL 语句输入应用，系统将自动进行格式美化，并基于静态规则引擎提供性能调优建议，最终输出优化后的 SQL 语句。

### 1.2 核心功能

- **SQL 格式化**：自动美化 SQL 代码，支持语法高亮显示
- **性能调优建议**：基于 AST 分析和表元数据，提供深度性能优化建议
- **优化后 SQL 生成**：对可自动改写的规则，直接生成优化后的 SQL
- **表元数据管理**：支持手动导入 DDL，提升分析精度
- **多方言支持**：支持 Impala SQL 和 Oracle SQL 两种方言

### 1.3 技术选型

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| 桌面框架 | Electron | 跨平台桌面应用 |
| 前端框架 | React 18 + TypeScript | UI 组件化开发 |
| 代码编辑器 | Monaco Editor | VS Code 同款编辑器，支持语法高亮 |
| SQL 解析 | ANTLR4 + 自定义 Grammar | 支持 Impala/Oracle 两种方言 |
| 规则引擎 | 自研 TypeScript 规则引擎 | 基于 AST 的静态分析 |
| 状态管理 | Zustand | 轻量级状态管理 |
| 样式方案 | Tailwind CSS | 快速 UI 开发 |

### 1.4 运行模式

**完全离线模式**：应用不联网，所有格式化规则、性能调优建议都基于本地规则引擎/AST 分析实现，不调用任何外部 API 或 LLM。

## 3. SQL 解析与格式化引擎

### 3.1 SQL 解析方案

**ANTLR4 Grammar 策略：**

- **Impala SQL Grammar**：基于 Impala 官方语法定义，覆盖常用语句（SELECT/INSERT/CREATE/ALTER/DROP）
- **Oracle SQL Grammar**：使用社区维护的 Oracle PL/SQL Grammar，支持 Oracle 特有函数和语法

**解析流程：**

```
用户输入 SQL
    ↓
选择方言类型
    ↓
ANTLR4 Lexer → Token 流
    ↓
ANTLR4 Parser → AST（抽象语法树）
    ↓
AST 遍历器 → 提取结构化信息
    ↓
传递给格式化引擎 / 规则引擎
```

### 3.2 格式化引擎

**核心能力：**

1. **语法高亮**：Monaco 编辑器内置支持，根据方言切换高亮规则
2. **自动缩进**：基于 AST 层级关系，自动计算缩进深度
3. **关键字大写/小写**：可配置 SQL 关键字的大小写风格
4. **换行规则**：
   - `SELECT` 字段列表：每个字段一行
   - `JOIN` 条件：独立一行
   - `WHERE` 条件：每个条件一行（可选）
   - 子查询：独立缩进块

**格式化配置选项：**

| 配置项 | 可选值 | 默认值 |
|--------|--------|--------|
| 关键字大小写 | UPPER / lower | UPPER |
| 缩进空格数 | 2 / 4 | 2 |
| 字段列表换行 | 每个字段一行 / 紧凑 | 每个字段一行 |
| WHERE 条件换行 | 每个条件一行 / 紧凑 | 每个条件一行 |
| 子查询缩进 | 独立块 / 内联 | 独立块 |

### 3.3 错误处理

- **语法错误**：ANTLR 解析失败时，在 Monaco 编辑器中标记错误位置（红色波浪线）
- **方言不匹配**：提示用户检查是否选择了正确的方言
- **部分解析**：即使有语法错误，仍尝试格式化已解析的部分

## 4. 性能调优规则引擎

### 4.1 规则引擎架构

```
AST + 元数据
    ↓
规则加载器（按方言筛选适用规则）
    ↓
规则执行器（逐条规则遍历 AST）
    ↓
问题收集器（聚合所有发现的问题）
    ↓
建议生成器（生成优化建议 + 优化后的 SQL）
```

### 4.2 规则分类

#### 4.2.1 通用规则（两种方言通用）

| 规则 ID | 规则名称 | 说明 |
|---------|---------|------|
| R001 | 避免 SELECT * | 建议明确列出需要的字段，减少 IO |
| R002 | 避免笛卡尔积 | 检查 JOIN 是否缺少 ON 条件 |
| R003 | 子查询改写为 JOIN | 相关子查询通常可改写为 JOIN 提升性能 |
| R004 | 避免在 WHERE 中对字段使用函数 | 如 `WHERE YEAR(date_col) = 2024` 会导致索引失效 |
| R005 | LIKE 前缀通配符检测 | 如 `LIKE '%abc'` 无法利用索引 |
| R006 | UNION 改写为 UNION ALL | 不需要去重时应使用 UNION ALL |
| R007 | 避免隐式类型转换 | 检查 JOIN/WHERE 中字段类型是否一致 |
| R008 | EXISTS 替代 IN (子查询) | 大表场景下 EXISTS 通常更高效 |

#### 4.2.2 Impala 专属规则

| 规则 ID | 规则名称 | 说明 |
|---------|---------|------|
| I001 | 分区字段必须使用 | 检查查询是否利用了分区键过滤 |
| I002 | JOIN 顺序优化 | 大表放左边，小表放右边（Broadcast Join） |
| I003 | 避免数据倾斜 | 检查 JOIN 键的分布，提示可能的倾斜风险 |
| I004 | 使用合适的 JOIN 类型 | 提示 `[SHUFFLE]` / `[BROADCAST]` hint 的使用场景 |
| I005 | COUNT(DISTINCT) 优化 | 大数据量时建议改写为 GROUP BY + COUNT |
| I006 | 统计信息缺失 | 提示用户对大表执行 `COMPUTE STATS` |

#### 4.2.3 Oracle 专属规则

| 规则 ID | 规则名称 | 说明 |
|---------|---------|------|
| O001 | 索引使用检测 | 基于元数据检查 WHERE 字段是否有索引 |
| O002 | 避免函数包裹索引字段 | 同 R004，Oracle 下特别重要 |
| O003 | 分页查询优化 | 避免 `OFFSET ... FETCH` 大偏移量，建议基于游标分页 |
| O004 | 避免 OR 导致全表扫描 | 建议改写为 UNION 或使用复合索引 |
| O005 | 提示 Hint 使用 | 检测是否可以使用 `/*+ INDEX */` 等 Hint 优化 |

### 4.3 元数据感知分析

用户通过粘贴 DDL 导入表元数据后，引擎解析出：

- 表名、字段名、字段类型
- 分区键（PARTITIONED BY）
- 存储格式（PARQUET/ORC/TEXTFILE 等）

**基于元数据的增强分析：**

- 检查 JOIN 字段类型是否匹配（避免隐式转换）
- 检查 WHERE 字段是否分区键（Impala）
- 检查 WHERE 字段是否有索引（Oracle）
- 检测数据倾斜风险（JOIN 键字段类型 + 表存储格式）

### 4.4 建议输出格式

每条建议包含：

```typescript
interface Issue {
  ruleId: string;              // 规则 ID，如 "I001"
  severity: 'warning' | 'error' | 'info';
  title: string;               // 问题标题
  description: string;         // 详细描述
  location: {
    line: number;
    column: number;
  };                           // 问题在 SQL 中的位置
  suggestion: string;          // 优化建议
  optimizedSql?: string;       // 优化后的完整 SQL（如可自动生成）
}
```

### 4.5 优化后 SQL 生成

- 对于**可自动改写**的规则（如 `SELECT *` 展开、`UNION` → `UNION ALL`、子查询→JOIN），直接生成优化后的 SQL
- 对于**需要人工判断**的规则（如数据倾斜、JOIN 顺序），只给出建议，不自动生成
- 优化后的 SQL 在右侧 Monaco 编辑器中以 diff 视图展示（红色=删除，绿色=新增）

## 6. 数据存储与错误处理

### 6.1 数据存储策略

#### 6.1.1 表元数据存储

**存储位置：** 本地文件系统（`~/.auto-sql/metadata/`）

**存储格式：** JSON 文件，每个表一个文件

```json
{
  "tableName": "orders",
  "dialect": "impala",
  "columns": [
    { "name": "id", "type": "BIGINT" },
    { "name": "user_id", "type": "BIGINT" },
    { "name": "amount", "type": "DECIMAL(10,2)" },
    { "name": "dt", "type": "STRING" }
  ],
  "partitionKeys": ["dt"],
  "storageFormat": "PARQUET",
  "importedAt": "2024-01-15T10:30:00Z"
}
```

**管理功能：**
- 查看已导入的表列表
- 删除单个表元数据
- 清空所有元数据
- 导出/导入元数据备份（JSON 格式）

#### 6.1.2 用户配置存储

**存储位置：** Electron 的 `localStorage` 或配置文件（`~/.auto-sql/config.json`）

**存储内容：**
- 方言选择（Impala / Oracle）
- 格式化偏好（关键字大小写、缩进、换行风格）
- 规则开关状态
- 窗口布局（各窗口大小、位置）
- 最近使用的 SQL 历史（可选，最多 10 条）

### 6.2 错误处理机制

#### 6.2.1 SQL 解析错误

| 错误类型 | 处理方式 |
|---------|---------|
| 语法错误 | 在输入窗口标记错误位置（红色波浪线），显示错误信息 |
| 方言不匹配 | 提示「检测到语法错误，请检查是否选择了正确的方言」 |
| 不支持的语法 | 提示「当前版本不支持此语法，将尝试部分解析」 |

#### 6.2.2 规则执行错误

| 错误类型 | 处理方式 |
|---------|---------|
| 元数据缺失 | 跳过依赖元数据的规则，显示提示「部分规则因缺少表元数据未执行」 |
| 规则执行异常 | 捕获异常，跳过该规则，记录日志，不影响其他规则执行 |
| 优化生成失败 | 只给出建议文本，不生成优化后 SQL |

#### 6.2.3 用户提示

**错误提示方式：**
- **Toast 通知**：右上角弹出，3 秒自动消失（如「格式化完成」「发现 3 个问题」）
- **模态对话框**：严重错误（如「DDL 解析失败」）
- **内联提示**：编辑器内的错误标记（红色波浪线 + hover 显示详情）

### 6.3 日志记录

**日志级别：**
- `INFO`：正常操作（如「导入 DDL 成功」「格式化完成」）
- `WARN`：可恢复的问题（如「规则执行跳过」「部分解析失败」）
- `ERROR`：严重错误（如「解析器崩溃」「文件写入失败」）

**日志存储：**
- 文件：`~/.auto-sql/logs/app.log`
- 轮转：每天一个文件，保留最近 7 天
- 大小限制：单个文件最大 10MB

**日志查看：**
- 设置面板中提供「查看日志」按钮
- 打开日志文件所在目录

### 6.4 性能考虑

- **大 SQL 处理**：超过 1000 行的 SQL，解析时显示进度提示
- **异步执行**：规则引擎在 Web Worker 中运行，避免阻塞 UI
- **缓存机制**：相同 SQL + 相同配置，缓存解析结果（LRU 缓存，最多 50 条）

```typescript
describe('Rule R001: 避免 SELECT *', () => {
  it('应检测到 SELECT *', () => {
    const sql = 'SELECT * FROM orders';
    const issues = ruleEngine.analyze(sql, 'impala', {});
    expect(issues).toContainEqual(
      expect.objectContaining({ ruleId: 'R001', severity: 'warning' })
    );
  });

  it('不应误报明确字段列表', () => {
    const sql = 'SELECT id, name FROM orders';
    const issues = ruleEngine.analyze(sql, 'impala', {});
    expect(issues.filter(i => i.ruleId === 'R001')).toHaveLength(0);
  });
});
```

- **类型安全**：TypeScript strict 模式

- **分支策略**：`main` (稳定) → `develop` (开发) → `feature/*` (功能分支)

### 10.2 扩展新规则

添加新规则只需 3 步：

1. 在 `src/engine/rules/` 对应方言目录下新建文件
2. 继承 `Rule` 基类，实现 `analyze(ast, metadata)` 方法
3. 在规则注册表中注册

```typescript
// 示例：新增一条 Impala 规则
export class I007_AvoidDistinctOnLargeTable extends Rule {
  id = 'I007';
  severity = 'warning';
  title = '避免在大表上使用 COUNT(DISTINCT)';

  analyze(ast: AST, metadata: Metadata): Issue[] {
    // 实现分析逻辑
  }
}
```

### 10.3 扩展新方言

1. 添加 ANTLR Grammar 文件（`.g4`）
2. 实现对应 Parser 和 Formatter
3. 添加方言专属规则目录

## 11. 总结

### 核心设计要点

| 要点 | 决策 |
|------|------|
| 技术栈 | Electron + React + TypeScript + Monaco Editor |
| SQL 方言 | Impala SQL、Oracle SQL（两种模式） |
| 运行模式 | 完全离线，无外部 API 调用 |
| 解析方案 | ANTLR4 + 自定义 Grammar |
| 分析深度 | 深度分析，支持 DDL 元数据导入 |
| UI 布局 | 四窗口独立面板，可拖拽调整 |
| 操作方式 | 全部按钮操作，无快捷键 |
| 结果展示 | Monaco Editor 语法高亮 + Diff 视图 |
| 数据存储 | 本地 JSON 文件 + localStorage |
| 打包发布 | NSIS 安装程序 + 免安装便携版 |

### 关键成功指标

1. **格式化准确性**：支持 Impala/Oracle 常用语法，格式化后语法高亮正确
2. **规则覆盖率**：通用规则 8 条 + Impala 规则 6 条 + Oracle 规则 5 条，共 19 条
3. **元数据感知**：支持 DDL 导入，基于表结构给出精准建议
4. **用户体验**：四窗口独立布局，操作流畅，结果直观
5. **性能**：大 SQL（1000+ 行）解析不卡顿，规则引擎异步执行
